# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**FoxPilot** — AI browser automation via MCP. npm package `foxpilot-mcp`; repo `balakumardev/foxpilot`.

## Commands

```bash
npm install                          # all deps (postinstall installs every subproject)
npm run build                        # build all via nx
cd mcp-server && npm run build        # individual builds (also: firefox-extension, chrome-extension)
cd firefox-extension && npx jest      # tests (chrome-extension also has a jest suite)
cd chrome-extension && npx jest
cd mcp-server && npm start            # start MCP server (auto-starts the broker)
cd mcp-server && npm run pack-dxt     # package the .dxt
npm run package --prefix chrome-extension   # build + zip -> chrome-extension/web-ext-artifacts/foxpilot-chrome-<v>.zip
```

## Architecture

Monorepo, five projects:
1. **mcp-server** — Node MCP server (stdio to the client) plus the **broker** (`broker-main.ts` / `broker.ts` / `broker-protocol.ts`).
2. **firefox-extension** — MV2 (background script + `browser.tabs.executeScript`).
3. **chrome-extension** — MV3 (service worker + offscreen document + content-script messaging).
4. **common** — shared message interfaces (`@foxpilot/common`).
5. **input-sidecar** — native-input helper.

### Communication flow
- Client ↔ MCP server: MCP over stdio.
- MCP server ↔ extension: through a **broker** on port 8089 (WebSocket). The broker is a separate, persistent process that holds the extension connection; multiple browsers (Chrome/Firefox) can connect and one is the active driver (`list-browsers` / `select-browser`).
- Auth: zero-config by default. The broker admits an extension based on the connection being loopback with a `chrome-extension://`/`moz-extension://` Origin — no user-typed secret. The control leg (MCP server ↔ broker) is signed with an auto-managed secret the mcp-server persists at **`~/.foxpilot/control-secret`** (mode 0600, created on first run, all server instances converge on it). A manual `EXTENSION_SECRET` is only set for remote/CONTAINERIZED deployments (where loopback+Origin gating doesn't apply); the same secret must then be set in the extension's Advanced settings. The broker binds both IPv4 and IPv6 loopback. `EXTENSION_PORT` defaults to 8089.
- Wire-protocol frames on `/extension` (post-zero-config): broker sends an explicit **`welcome`** ack on accept (typed **`rejected`** reason on refusal); the connection status pill flips "Connected" only on this ack, not on socket-open (the old socket-open-flip was the "Connected ↔ Disconnected flicker on wrong secret" failure mode). A **`healthcheck`** frame round-trips the broker's `/health` snapshot (server up, `extensionConnected`, browser count, active or standby) and powers the **Test Connection** button.

### Key files
- `mcp-server/server.ts` — tool definitions; `mcp-server/broker.ts` — broker.
- `firefox-extension/message-handler.ts`, `chrome-extension/message-handler.ts` — execute browser actions. Both have a `switch(req.cmd)` whose `default:` uses a `const _exhaustiveCheck: never = req` tripwire — adding a `cmd` to the `ServerMessage` union forces a matching case or compile fails.
- `firefox-extension/injected/*` — functions stringified and run in the page (`action-script`, `snapshot-script`, `page-world`, `upload-script`, `point-action-script`, `screenshot-script`). Mirrored in `chrome-extension/injected/*`. **For new modules, the function bodies (or trailing code past `export function`) must be byte-identical between the two extensions** — header / doc-comment lines are allowed to diverge. Mirror manually. `self-containment.test.ts` only checks the FIREFOX copies are stringify-safe — `mirror.test.ts` is what actually compares the two extensions (`page-world.ts` excluded; see the gotcha below).
- `chrome-extension/cdp-input.ts` — refcounted `chrome.debugger` attach by `purpose: "network" | "input"` (Phase 3, v1.0.13). Detaches only when the last purpose releases; `capture-response-bodies` defaults purpose to `"network"` so its tests/exports are unchanged. Coexist with `network-capture.ts`.
- `mcp-server/point-format.ts`, `mcp-server/network-format.ts`, `mcp-server/snapshot-format.ts` — server-side formatters for the new tools (unit-tested in isolation).
- `firefox-extension/browser-http.ts`, `chrome-extension/browser-http.ts` — background-context HTTP/cookie/stream logic for the privileged tools (auto-bundled via `background.ts` import chain).
- `common/server-messages.ts`, `common/extension-messages.ts` — message types.

## Gotchas (these cost real time)
- **Isolated vs page world / CSP:** DOM ops (click, fill, snapshot, **upload-file**) run in the ISOLATED content-script world and are CSP-immune. `evaluate-script` (world:"main") / `handle-dialog` / `emulate` inject a page-world `<script>`, which **strict-CSP pages (e.g. chrome.google.com) block** → "Timed out waiting for in-page result" / "Invalid message signature". Don't add page-world `<script>` injection for anything that can run in the isolated world. `upload-file` was migrated to the isolated world in v1.0.8 (was previously page-world injection — CSP-blocked on the CWS dev console; fixed by `performFileUpload` + resolving the hidden `<input type=file>` from the dropzone since hidden inputs aren't snapshotted). On Firefox, File/DataTransfer still cross the Xray boundary via `wrappedJSObject` + `cloneInto`.
- **`evaluate-script world:"isolated"` (v1.0.13):** goal = CSP-immune eval, but **Firefox full, Chrome MV3 honestly degrades**. Chrome removed string-eval from `chrome.scripting`; arbitrary source requires `new Function` and the default isolated-world extension CSP blocks it → returns a clear `ok:false` naming the CSP-immune alternatives (snapshot / coord tools / `get-cookies`). **Do NOT add `unsafe-eval` to the Chrome manifest** to fix it — uncertain MV3 support + expands attack surface + **would very likely flag the Chrome Web Store review** (which fires on every push to `main`). The chosen posture: Firefox gets full, Chrome gets an honest message, the practical escape for `app.factors.ai`-class pages is snapshot + coord + cookies + the CDP engine tier — not `world:"isolated"`.
- **`evaluate-script` `world:"auto"` + `engine:"cdp"` (v1.0.14):** **`world:"auto"` is now the DEFAULT** (was `"main"`). Firefox `world:"auto"`: tries `main` then transparently retries `isolated` on CSP failure (genuinely works there). Chrome `world:"auto"`: tries `main`, on CSP failure returns a **fast, definitive `ok:false`** naming the escapes — does NOT auto-retry isolated (it'd just hit the same `new Function` wall — wasted time). `world:"main"` / `"isolated"` remain explicit-force (no fallback) → existing callers unchanged. **NEW `engine:"cdp"`** opt-in (Chrome/Edge only; Firefox rejects cleanly): attaches `chrome.debugger`, runs `Runtime.evaluate({returnByValue:true, awaitPromise:true, userGesture:true})`, detaches in `finally`. **CSP-immune** — bypasses page CSP entirely (same debugger tier as `capture-response-bodies`). `engine:"cdp"` overrides `world`. `DebuggerPurpose` extended to include `"eval"` alongside `"network"` / `"input"`; new file `chrome-extension/cdp-eval.ts` mirrors `cdp-input.ts`'s shape. CSP detection is a synchronous **"started" marker** (first statement of the injected IIFE) — absent after `appendChild` = instant `cspBlocked:true, ok:false`, NOT the old 10s guess. The **10s eval backstop stays** (a legit `await fetch()` eval needs it); the marker fails fast without shortening it.
- **Background-context tools exist for CSP/cookie/WAF escape** (`get-cookies {url?, domain?, names?: string[]}`, `browser-fetch`, `stream-start`/`poll`/`close`): these run in the **extension background context** (MV3 service worker / MV2 persistent page), which is governed by the EXTENSION's CSP, not the page's, and can use the browser's real cookie jar. Use them when `evaluate-script` is blocked by a strict page `script-src` AND you need cookie-authed requests (incl. httpOnly cookies, WAFs that 403 curl). See `chrome-extension/browser-http.ts` and `firefox-extension/browser-http.ts`. `names` is plural (was a single `name` in v1.0.12); empty array deliberately fail-opens to all cookies — gated behind perms + the caller's own intention.
- **Tiered network capture** (`get-network-requests` is the covert default; `capture-response-bodies` is the opt-in debugger tier). Covert `webRequest` captures headers (incl. `Cookie`/`Set-Cookie`/`Authorization` on Chrome via `extraHeaders`, plain on Firefox) + request bodies — invisible to the site. **Chrome MV3 CANNOT capture response bodies covertly** (no `filterResponseData`, no debugger without opt-in). The opt-in `capture-response-bodies { tabId, enabled }` tool attaches `chrome.debugger` (CDP) to that one tab → captures full response bodies, but **shows the "started debugging this browser" banner and is detectable by anti-bot → this BREAKS covert**. The tool's own description tells the model when to reach for it; only use it when you genuinely need a response body on Chrome/Edge. `enabled:false` detaches; auto-detaches on tab close / Automation-off / DevTools-dismissed. Needs the `"debugger"` manifest permission on Chrome (expands CWS review scope — the release still ships, but Google's review is async). **`get-network-requests {includeHeaders, includeBody, includeCredentials}`** — credential values are REDACTED by default; `includeCredentials: true` opt-in returns the real `Cookie`/`Authorization` values un-redacted (only effective when `includeHeaders:true`).
- **`take-snapshot` schema (v1.0.13, Phase 1):** all optional, all back-compat preserved. `selector?: string` (CSS selector → synthetic `<select>` rows so the next `click-element` works on a uid); `textContains?: string` (case-insensitive, leaf-preferring text match; role-less `<div>` leaves get a text-mode-local `textContent` name fallback so the row is labelled rather than `clickable ""`); `rootSelector?: string` (scopes snapshot to subtree; invalid → `error?` on the message, server maps to `isError`); `offset?: number` + `limit?: number` (paging in DOM order); `includePointer?: boolean = true` (promotes `cursor:pointer` `<div onclick>` into the default pass — the React-SPA fix); `maxInteractive?: number = 80` (caps cursor:pointer enumeration in the default pass). Response includes `total` + `hasMore`; a `[uid=eN]` is valid **only until the next snapshot on that tab** (snapshot → act → snapshot again). Default output now always prefixes a count line — the actual literal is `[snapshot: N elements]` (NOT `Total: N elements.`), with the truncation / `more via offset/limit` / docState hints folded into that same bracket — so a cold agent knows it's not seeing the page.
- **`wait-for-text` accepts `string | string[]`** (v1.0.13): string path byte-unchanged; array OR-matches and returns `{matched: "<the value that matched"}` in the response.
- **`scroll-to` / `scroll-into-view` tools (v1.0.13, Phase 2):** both run in the isolated world — `scroll-to({x, y, dx, dy})` is a thin wrapper, `scroll-into-view({uid})` uses the existing uid-to-element resolver. Inner-container scroll is via `scroll-at` (nearest scrollable ANCESTOR at the point) — `press-key PageUp` only scrolls the window, which is the gap.
- **Coordinate tools — `click-at` / `type-at` / `hover-at` / `scroll-at` (v1.0.13, Phase 2+3):** all take `{x, y, engine?: "synthetic" | "cdp", ...}`. Engine is the central feature: **synthetic** = isolated-world `elementFromPoint` + dispatch (default, covert, `isTrusted:false`); **cdp** = Chrome/Edge only, attaches `chrome.debugger` via refcounted `purpose:"input"` and fires `Input.dispatchMouseEvent` / `Input.insertText` for trusted events with `isTrusted:true` — same banner tradeoff as `capture-response-bodies`. Off-point → no dispatch at all. Return `{ok, element: {tag, text, rect, accessibleName}}`; coords are **viewport CSS px** (= screenshot px ÷ devicePixelRatio, ~2× on Retina/Edge). Synthetic limitations: `type-at`'s `execCommand("insertText")` relies on the focus sequence placing a caret — strict rich-text editors (Lexical/ProseMirror/Slate) may ignore it; **use `engine:"cdp"` to upgrade** on Chrome/Edge (CDP click → editor's own caret logic → `insertText`). `hover-at` synthetic does NOT cross shadow DOM and does NOT trigger CSS `:hover`/pointer-driven rules. On Firefox: `engine:"cdp"` returns a clear error (no debugger API).
- **`engine:"cdp"` extended to UID input tools (v1.0.18 — the non-covert parity feature):** before v1.0.18 only the coordinate tools had `engine:"synthetic"|"cdp"`, so snapshot→uid could never reach DevTools parity. Now `click-element` / `fill-element` / `fill-form` / `press-key` / `hover-element` accept the same `engine?` flag (default `synthetic` = back-compat). CDP path branches in `runInputAction` before the synthetic dispatch, is **not** wrapped in `raceInputAgainstNavigation` (CDP fires from background, wins the nav race naturally), and uses the existing `purpose:"input"` refcounted `chrome.debugger` attach. New `chrome-extension/cdp-input.ts` helpers: `cdpInputFill` (focus-click → select-all Ctrl/Cmd+A → `Input.insertText`), `cdpInputKey` (keyDown/keyUp with key→code→windowsVirtualKeyCode map, modifier bitmask Alt=1/Ctrl=2/Meta=4/Shift=8, `text` suppressed under command modifiers). Firefox rejects `engine:"cdp"` with a clean `ok:false` before any page work. `drag-element` and `select-option` are still synthetic-only; `type-text` is not wired (the 5 listed are the full CDP uid set). Coordinate space: `readElementRect` returns viewport CSS px from `getBoundingClientRect()` + `scrollIntoView({block:"center"})`s the element first; center = `rect.x + width/2, rect.y + height/2`.
- **Covert `keyCode` does NOT cross isolated→page world (v1.0.18 Finding #1, documented honest limitation):** covert `press-key`/type deliver `e.key` + `e.code` to page-world React (native-backed, cross the world boundary fine) but **`e.keyCode` / `e.which` stay 0** — the `defineProperty` expando set on the isolated-world `KeyboardEvent` doesn't reach the page-world event React reads. So React code that gates on `e.keyCode===13` (older API) needs **`engine:"cdp"`**, which delivers real `keyCode:13`. This is inherent (fixing it needs page-world `<script>` injection = strict-CSP-risky). It matches the two-mode design exactly: covert = max it safely can (`key` + `code`); non-covert = full parity (`keyCode` + everything else). Verified live on the React fixture: covert returns `key:"Enter", code:"Enter", keyCode:0`; CDP returns `key:"Enter", code:"Enter", keyCode:13`.
- **Covert event-fidelity fixes (v1.0.18, A1-A7) — drives React SPAs without CDP:** every isolated-world `injected/*` event was rebuilt to what React/typical SPA frameworks actually observe. **A1 keys** carry `code` (init dict) + `keyCode`/`which` (set via `Object.defineProperty` AFTER construction — Chrome ignores them in the init dict) + `keypress` between keydown/keyup for printable chars. **A2 checkbox/radio `fill`** drives the single-activation `dispatchClickSequence(el)` (the covert click) instead of assigning `.checked` — React's `ChangeEventPlugin.shouldUseClickEvent` binds `onChange` to the click, not `input`/`change`. **A3 click sequence** is now `pointerover → pointerenter → pointermove → pointerdown → mousedown → focus() → pointerup → mouseup → click()` (+dblclick) with `buttons:1→0`, `button:0`, `composed:true` (so events cross shadow DOM). **A4 coordinates** on every mouse/pointer event (uid path = `getBoundingClientRect()` center, point path = `args.x/y`; `pageX/pageY` derive natively from clientX/Y+scroll). **A5 `contenteditable`** uses a cancelable `beforeinput` (`InputEvent` with `inputType:"insertText"`, `data`) + `input` — and **skips** `input` when `beforeinput` was canceled (Lexical/ProseMirror/Slate drive their own model); falls back to `Event`+`defineProperty` where `InputEvent` is absent. **A6 `<select> fill`** resolves by `.value` OR trimmed visible text/label, sets via the native `HTMLSelectElement.prototype` value setter (React tracks the native value), fires `input`+`change`. **A7 hover** emits `pointerover/pointerenter/pointermove` alongside mouse events. All A1-A7 changes byte-identical across the two extensions; `mirror.test.ts` is the cross-extension guard (`self-containment.test.ts` only checks stringify-safety of the Firefox copies). New behavior tests in both `action-script.test.ts` and `point-action-script.ts`'s test.
- **Snapshot safety (v1.0.18, B10/B11):** **B10** stamps each interactive node with `data-bcmcp-sig` (`tag|role|id|aria-label|name|data-testid`) at snapshot time; `performInputAction`'s `resolve()` reads the live sig on the element the uid points to and returns `ok:false, error:"uid stale — take a fresh snapshot"` if it changed — without B10, React node recycling (lists re-ordering, remounts) silently reuses the `data-bcmcp-uid` on a different element and the click lands on the wrong control. **B11** `isHidden` now checks `getComputedStyle` for `display:none` / `visibility:hidden|collapse` (was inline-style-only — missed React subtrees whose parent applies `display:none` via a stylesheet) + a `layoutActive`-gated 0×0 geometry check + a terminating ancestor walk. **Deliberately does NOT exclude `opacity:0`** — those elements are still interactive (a11y-tree-present, focusable, clickable; the standard visually-hidden file-picker pattern). The B11 test was updated to assert opacity:0 is **kept** while `visibility:hidden` is still excluded.
- **CDP `describe-at` ordering (Important — final review caught it):** in Chrome `message-handler.ts` `dispatchCdpPointAction`, capture the element descriptor **BEFORE** the trusted dispatch. A CDP click that navigates/mutates then re-runs `elementFromPoint` against the new DOM and either returns a wrong descriptor or — worse — fires a false-positive `click-element` on the wrong target (double-submit risk). Pattern: resolve → validate the point → describe → dispatch → return the pre-captured descriptor; off-point → no dispatch at all.
- **Navigating input actions must nav-race (v1.0.14):** clicking a link whose onclick sets `window.location.href = "<cross-origin>"` USED TO HANG — the cross-origin nav tears down the content-script world before the ack flushes, so the reply never resolves or rejects, the 5s broker timer fires, and the user sees "Timed out waiting for response from the browser extension". This affects **all input modes** on both extensions: click-element (`runInputAction` synthetic dispatch), click-at/type-at (`runPointAction` synthetic branch), fill, fill-form, press-key — including the `native` synthetic fallback (a reviewer caught that gap; wrap-all was the rule). CDP paths (click-at `engine:"cdp"`) already fire from background and win the race naturally. **Fix:** shared background helper `raceInputAgainstNavigation(tabId, dispatchPromise)` in `nav-race.ts` (both extensions; only the `chrome`/`browser` global + doc comments differ) — register one-shot `tabs.onUpdated` for `tabId` + `status:"loading"` before dispatch, `Promise.race` against the reply, nav wins → `{ok:true, navigated:true}` (additive on `actionResult` / `pointResult`), listener removed in `finally`. `navigated` is now surfaced in `click-element` / coord-tool output. No new permissions (`tabs` already present; `webNavigation` deliberately not added — would expand CWS review scope). No timeout bump. **One accepted edge (documented):** a coincidental top-frame load within the ms window of a failed click could mask it as `navigated:true` — `tabs.onUpdated`-inherent, low probability, grace-period mitigation deliberately skipped as not worth the risk. **2026-07-27 third arm — the leak plug:** when BOTH the content-script ack and the `tabs.onUpdated` nav signal hang (frozen / bfcached content-script world + a same-document/iframe/beforeunload nav that never fires `status:"loading"`), the `finally` never runs and the listener leaks for the life of the MV3 SW — and each leaked listener then resolves an UNRELATED later click as `{ok:true, navigated:true}` (reports success for a click that never happened; false positive is strictly worse than a timeout). A deadline arm (`LEAK_PLUG_MS = 60000`, pinned to `REQUEST_TIMEOUT_MS`) guarantees the promise settles; invariant is `LEAK_PLUG_MS >= largest per-command budget in mcp-server/timeouts.ts` (45000 today). Resolves `ok:false, error:"outcome is UNKNOWN"` (never `ok:true`); resolves rather than rejects because `browser-api.ts:552` throws on `ok:false` either way, and resolving keeps the signed action-result's append-only fields (`navigated`/`intercepted`/`element`/`selected`) intact.
- **`take-screenshot` "image readback failed" (v1.0.14):** Chromium's `captureVisibleTab` rejection was being passed through verbatim with no paint-settle. The existing `captureWindowWithRetry` helper (3 tries, `[100,300,600]`ms backoff) was previously only wired into `captureFullPage` — the default viewport + element paths now use it too, which absorbs the transient post-activation / mid-nav GPU readback failure. `captureFullPage` fallback's `catch(e)` now preserves the real error as `"image readback failed: " + e.message` instead of discarding `e`.
- **`take-screenshot` CDP fallback is acceptable to Bala (2026-07-27) — but it MUST be surfaced, not silent.** When the default viewport path's three `captureVisibleTab` retries all return empty (a persistent GPU/compositor failure some configs hit), the tool falls back to a CDP screenshot, which briefly shows the "started debugging this browser" banner and is detectable by the page. The reply already renders a `Warning:` line ahead of the image when this fires. **Only the default viewport path falls back** — `fullPage` and element (`uid`) captures fail instead, and Firefox has no fallback. The fallback is fine when it's loud; use `take-snapshot` for covert reads when banner-detection is a problem.
- **`take-screenshot` "Tabs cannot be edited right now (user may be dragging a tab)" (v1.0.19):** `chrome.tabs.update({active:true})` inside `withTabActivated` (which MUST activate the tab before `captureVisibleTab`) transiently throws this drag-detection false positive when the tab strip is mid-mutation. The existing `captureWindowWithRetry` only wraps `captureVisibleTab` itself, so the activation throw was un-retryable. New `activateTabWithRetry(tabId)` helper (both extensions, byte-identical): 3 attempts at `[100,300,600]`ms backoff, retries ONLY on `/dragging a tab|Tabs cannot be edited/i` — any other error (tab closed / invalid id) rethrows immediately so the tool still fails fast. Restore inside the `finally` is best-effort (own try/catch) so a transient restore failure can't discard a successful capture nor mask an `fn()` error. `[100,300,600]` backoff matches the existing capture-retry convention by design (the third value is dead in both helpers — the 3 attempts produce 2 gaps).
- **CDP click interception parity (v1.0.19, the real fix for #1 in the `click-element succeeds but page doesn't react` pattern):** before v1.0.19 the **synthetic** path had interception detection (reads `elementFromPoint` at center → `classifyHit` → surfaces "⚠ intercepted" by default; honors `failIfIntercepted`), but the **`engine:"cdp"` path dispatched blind at the rect center** — a covering child/tooltip/overlay at that pixel swallowed the trusted click while the hover tooltip still showed, masking it. New **read-only `classify-intercept` action** in `performInputAction` (both extensions, byte-identical): reuses the existing inner `classifyHit`/`describeIntercept` and `scrollIntoView({block:"center", inline:"center"})` (matches `readElementRect`'s scroll exactly — a bare `block:"center"` defaults `inline` to `"nearest"` and hits at a different X on horizontally-scrollable targets, caught by review) → returns `{ok:true, intercepted?}`. The CDP click path runs this probe before dispatch, threads `intercepted` onto the action-result (server already appends the warning by default), and **honors `failIfIntercepted`** (hard-stop on cover — was previously ignored on CDP entirely, which a reviewer flagged as a parity gap since the change is titled "parity"). No new content-script case (uses `sendMessageToTabRaw`); no new `InputActionArgs` entries (the action is added to `performInputAction`'s inner union, not the outer exhaustive one). `mirror.test.ts` guards the byte-identical mirrors (`self-containment.test.ts` does not compare the two extensions).
- **`evaluate-script world:"isolated"` Chrome-CSP message names `engine:"cdp"` (v1.0.19, the actionable Fix B):** the `isError:true` honest-degrade message used to name only `world:"main"` + `take-snapshot`/`take-screenshot` — it OMITTED the exact `engine:"cdp"` escape the user had to discover on their own (the same shape the tool description already lists). The new message names `engine:"cdp"` + `world:"main"` + `take-snapshot`/`take-screenshot`/`coordinate tools`/`get-cookies` — the full set of CSP-immune alternatives. `isError` stays (the eval genuinely couldn't run). Chrome-only — Firefox `evalInIsolatedWorld` is `executeScript({code: new Function(...).toString()})` (compiles the source string, CSP-immune by design) and has no degrade branch.
- **`Cookie` header is a forbidden `fetch` header** (Chrome MV3) and is ignored if set directly. For `useSessionCookies` on `browser-fetch`, install a **temporary `declarativeNetRequest` session rule** (modifyHeaders, `urlFilter` scope, `["xmlhttprequest","other"]` resource types) around the fetch and remove in `finally`. On Firefox MV2, use a blocking `webRequest.onBeforeSendHeaders` listener (register lazily, unregister in `finally`). Default path is plain `credentials:"include"` — the browser attaches httpOnly cookies automatically. Reserved Chrome DNR id band for cookie rules is `210000+` (clear of `emulate.ts`'s `100000` UA-rewrite band).
- **Chrome MV3 SW idle orphans DNR rules:** the service worker can be killed mid-stream (~30s idle), losing the in-memory `Map<streamId, StreamSession>` while an installed `useSessionCookies` DNR rule persists. One-shot `browser-fetch` is safe (synchronous `finally`), but streams can orphan. Mitigation: `clearStaleCookieRules()` startup sweep in `chrome-extension/browser-http.ts`, invoked from `background.ts` init — clears any rule in the reserved `210000+` band. Pattern: pick a reserved id band for any long-lived DNR rule class and sweep on SW boot.
- **Zod 4.3.6 `z.record` gotcha:** in this repo's zod 4.3.6, `z.record(z.string())` infers `Record<string, unknown>` (v4 treats the single arg as the KEY schema, value defaults to `unknown`), not the v3 `Record<string, string>`. For `Record<string, string>` you MUST use the two-arg form: `z.record(z.string(), z.string())`. Single-arg form only valid as a key-only constraint.
- **Firefox file upload:** content scripts see the page via Xray; build File/DataTransfer in the page realm via `wrappedJSObject` + `cloneInto` so `input.files` accepts the FileList (see `injected/upload-script.ts`).
- **Stale broker:** the broker is a detached persistent process holding port 8089. After rebuilding mcp-server, `pkill -f dist/broker-main.js` so a fresh broker starts. Extension admission is origin-gated (loopback + `chrome-extension://`/`moz-extension://` Origin), so a user-secret mismatch is no longer the usual failure. The common transition issue after a broker rebuild: the still-loaded extension is older than the fresh broker — if tools report "no extension connected," **reload the extension** (Firefox: `about:debugging` → Reload). **Broker logs land at `~/.foxpilot/broker.log`** (mode 0600, 5 MB cap rotated on open plus in-lifetime 60s trim via `ftruncateSync(1, 0)` — degraded to `/dev/null` if the file can't be opened). Discovery path: `BrowserAPI: broker log -> /Users/balakumar/.foxpilot/broker.log` on the spawning client's stderr. Use this for late-reply / MV3-reconnect diagnostics — pre-2026-07-27 logs went to `/dev/null` (broker was spawned `stdio: "ignore"`).
- **Honest broker failure classification (2026-07-27, broker-side):** the blanket `"Timed out waiting for response from the browser extension"` was a lie about certainty and caused the agent to retry-and-double-click mutating commands. `mcp-server/broker-core.ts` now classifies per-cmd: **read-only `cmd`s** (11-entry `READ_ONLY_COMMANDS` allow-list — `get-tab-list`, `get-tab-content`, `take-snapshot`, `take-screenshot`, `wait-for-text`, `get-console-messages`, `get-network-requests`, `get-cookies`, `stream-poll`, `get-active-tab`, `get-browser-recent-history`) keep the original byte-identical string. **Everything else** gets MISSING-REPLY wording ("may already have been applied… do NOT blindly retry… verify state first"). Four named messages: `timeoutMessageFor(cmd, ms)`, `NEVER_SENT_MESSAGE` (submit-time guard caught it OR queued-then-extension-gone → SAFE to retry), `EXTENSION_GONE_IN_FLIGHT_MESSAGE` (extension died mid-flight → MISSING REPLY), `EXTENSION_GONE_QUEUED_MESSAGE` (extension died before dispatch → SAFE to retry). The allow-list has a compile-time exhaustiveness test on the `cmd` union — adding a new `cmd` to `common/server-messages.ts` without classifying it breaks the build rather than silently defaulting to the wrong side. **Per-browser scoping:** `PendingRequest.browserId?` + `failInFlightForBrowser` / `failInFlightForLongPoll` — `abandonTab` (NOT `completeTab`) on the failure path, so a queued `fill-element` for a disconnected browser's tab cannot be re-dispatched against a surviving browser. Leases are deliberately not cleared (they have no browser dimension and self-release on TTL + client disconnect).
- **Frozen background tab is named in input-action timeouts (v1.0.21, the fix for "click-element timed out but take-snapshot looked fine"):** the trap is that `get-tab-web-content`/`take-snapshot` with `activateTab:true` foregrounds the tab, runs, then **restores the user's previous tab** — leaving the target backgrounded. A subsequent `click-element` then eats its full 15s budget and reports MISSING REPLY, while `take-snapshot` on that same tab keeps returning a **full element tree**, so the tab looks perfectly healthy. That asymmetry is inherent: a snapshot is one synchronous DOM read, whereas covert input is paced by the background as **several sequential round-trips into the page** (see `humanize-steps.ts`), so a frozen renderer stalls input only. A plain `select-tab` then makes the identical click succeed instantly. **Fix:** new `TAB_DRIVING_COMMANDS` set in `broker-core.ts` (sibling of `READ_ONLY_COMMANDS`, typed `ServerMessage["cmd"][]` so a typo fails `tsc`) — the 11 input actions + `select-option` + `dismiss-overlays` + `scroll-to` + `scroll-into-view`. Their timeout **appends** a LIKELY-CAUSE clause naming the freeze, stating explicitly that a healthy snapshot does **not** rule it out, and giving the remedy as `select-tab` **first** (works for every command) then `activateTab:true`. `timeoutMessageFor` gained `opts.activateTabRequested`, read structurally off the request at the `dispatch()` timer site — when the call already passed `activateTab:true` the message **rules the freeze out** instead of telling the agent to redo what it just did. Read-only wording stays byte-identical (pinned by 3 equality assertions); `evaluate-script`/`upload-file` deliberately excluded (their dominant timeout cause is a strict page CSP, so "stalls input" would misdirect). **Deliberately NOT auto-activate-and-retry on timeout** — a MISSING REPLY may already have applied, so an automatic click retry is exactly the double-submit the v1.0.19 honest-failure work exists to prevent. **Known gap (not closed):** `click-at`/`type-at`/`hover-at`/`scroll-at` accept no `activateTab` at all (absent from their `server.ts` schemas and their `common/server-messages.ts` interfaces), which is why the hint leads with `select-tab`. Lives in `dist/broker-main.js` → **bounce the broker** to activate.
- **`[snapshot: 0 elements]` now self-describes (v1.0.21):** a bare 0-element tree was identical in three very different situations — a document **mid-navigation**, a **blank/torn-down** document, and a real page that genuinely has **no interactive controls**. `buildSnapshot` now returns `docState: {readyState, url, bodyChildren}` on its **success paths only** (the three early error returns already say why they returned nothing), read defensively next to the result so it describes the document the tree was actually built from. `snapshot-format.ts` folds a suffix into the existing count line plus one prose line: `NAVIGATING (readyState=…, url=…)`, `NO DOCUMENT CONTENT`, or `document loaded, nothing interactive matched` (which also names selector/textContains/rootSelector over-filtering, shadow roots and iframes). An unreadable `readyState` (`""`) is treated as navigating — "cannot vouch for this tree" beats "settled". A non-empty tree read off a still-loading document gets `, document still loading — tree may be incomplete`. **Stays a success, never `isError`** — the snapshot itself worked. `docState` is optional end-to-end, so an older extension keeps the previous output byte for byte (pinned by a back-compat test). Nothing in the repo read `document.readyState` before this. Lives in `dist/server.js` → **restart the client** (new session / Desktop quit+reopen); the extension half needs a reload.
- **`self-containment.test.ts` does NOT compare the two extensions (v1.0.21):** CLAUDE.md called it "the canonical guard" for the `injected/*` byte-identical mirror rule, but it only imports the **Firefox** copies and asserts each is stringify-safe (no `require(`/`import `/esbuild helpers, `.toString()` is a real body). It never opens the Chrome copies, so editing one `injected/*` file and forgetting its twin **broke no test** and shipped a fix to one browser only. `mirror.test.ts` now carries an `it.each` over the 8 genuinely-mirrored injected modules (`action-script`, `dismiss-overlays-script`, `humanize-steps`, `point-action-script`, `screenshot-script`, `select-option-script`, `snapshot-script`, `upload-script`) using the existing `normalize()` (strips the leading doc comment, collapses the `chrome`/`browser` global), plus a `readdirSync` completeness check so a NEW injected module fails the suite until it is classified. **`page-world.ts` is the one documented exclusion** — its two copies differ by ~125 lines and the divergence is real, not cosmetic (Chrome's isolated-world eval honestly degrades where Firefox compiles the source string); its own header still claims byte-identity with Firefox, which is stale. Verified non-vacuous: appending one line to the Chrome `snapshot-script.ts` fails the guard.

# Browser Testing with Chrome DevTools MCP

Chrome DevTools MCP **auto-launches Chrome** via puppeteer. No manual browser start needed.
Uses `--isolated` mode — each session gets its own temp Chrome profile for parallel safety.

Note: this is a *different* browser than the one FoxPilot's own extension automates. Use Chrome DevTools MCP to visually test this repo's own UI surfaces (e.g. the extension options page, `test-fixtures/csp-react-spa/`) — it does not exercise the FoxPilot broker/extension path itself.

## Quick Start

1. Start whatever needs serving (e.g. `node test-fixtures/csp-react-spa/server.mjs`, or open an options page file directly)
2. Start Claude Code in this directory — the MCP server starts automatically

## Available MCP Tools

| Tool | Description |
|------|-------------|
| `mcp__chrome-devtools__navigate_page` | Navigate to URL |
| `mcp__chrome-devtools__take_snapshot` | Get a11y tree with uids (preferred over screenshot) |
| `mcp__chrome-devtools__take_screenshot` | Visual screenshot |
| `mcp__chrome-devtools__click` | Click element by uid |
| `mcp__chrome-devtools__fill` | Type into input by uid |
| `mcp__chrome-devtools__evaluate_script` | Run JavaScript in page |
| `mcp__chrome-devtools__list_console_messages` | Get console output |
| `mcp__chrome-devtools__list_network_requests` | Get network requests |

**Prefer `take_snapshot` over `take_screenshot`** — snapshots return uids for direct interaction.

## Testing Workflow

1. Navigate to the page under test
2. Take a **snapshot** to see the a11y tree with uids
3. Interact using uids from the snapshot (click, fill)
4. Take another snapshot to verify the result
5. Check console/network logs if something goes wrong
